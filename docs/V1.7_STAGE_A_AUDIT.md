# LUMIO v1.7 — Stage A Stability Audit

**Audit date:** 2026-10-31  
**Audited source:** `feature/v1.6-home-folder-catalogue` at `c6e847a73e87101ac4b3f816d793913a93b82268`  
**Audit branch:** `audit/v1.7-stage-a`  
**Scope:** Read-only source/configuration review and release-readiness classification. No application behavior was changed in Stage A.

## Executive result

Stage A source review is complete. The current codebase has a usable foundation, but it is **not yet a v1.7 release candidate**. Several important capabilities are present in source but have no automated or physical-device evidence in the repository. The largest release risks are playback/decoder behavior, Music navigation correctness, storage-provider behavior, file-operation recovery, and Vault temporary-file/key recovery.

This is a source audit, not a device test. No statement below should be read as proof that a feature works on a physical phone.

## Fixed architecture and product constraints

- AndroidX Media3 / ExoPlayer remains the primary playback engine.
- NextLib remains the Media3 software-decoder extension.
- Do not add LibVLC or another heavyweight playback engine.
- Record baseline APK size and measure the APK after every major dependency change.
- APK hard ceiling: **45 MB**.
- Preserve the current player interface and avoid an engine migration.
- Primary physical-device target: Moto G32, Android 13.

## 2. Findings requiring action

### P0 — Playback and decoder reliability

1. No codec regression corpus or automated playback tests were found. CI validates JavaScript syntax and APK compilation/package only. It does not instantiate a player or verify decoded frames/audio.
2. The automatic HEVC path orders software decoders before hardware decoders. This is a policy, not proof that the chosen decoder supports the actual profile, bit depth, level, resolution or bitrate.
3. Playback failure logs Media3's error code and displays a generic failure dialog. User-facing diagnostics do not yet identify the attempted decoder, codec/profile, fallback sequence or actionable reason.
4. Player replacement when changing decoder preference preserves queue/index/position in source, but needs tests for playback state, audio focus, media-session continuity and error recovery.
5. The repository does not contain a reproducible sample inventory for H.264, HEVC 8-bit, HEVC Main 10, VP9, AV1, MPEG-4, common audio formats, corrupt/truncated files and high-bitrate edge cases.

**Required before v1.7 release:** documented codec matrix, decoder diagnostics, repeated open/close and next-item tests, graceful unsupported-file handling, and Moto G32 physical testing. Do not claim universal codec support.

### P0 — Music library correctness

1. Visible Music navigation exposes **Songs, Playlists, Albums, Artists, Folders, Recently played and Favorites**. The previously requested **Recently Added** view is not present as a distinct tab. Date added exists as a sort option, which is not equivalent to a Recently Added collection.
2. Folders is implemented as a folder list with exact-path drill-in. Verify nested paths, empty folders, metadata-less tracks and duplicate URIs.
3. Playlist persistence uses WebView localStorage and stores track URIs. Test files moved, deleted, permission-revoked or reindexed.
4. The inline player script contains earlier playlist rendering functions followed by later declarations with the same function names. Later declarations take precedence, but duplicate implementations increase maintenance and regression risk.
5. No automated tests were found for the Songs-versus-Folders regression.

**Required before v1.7 release:** test each tab independently, confirm Songs always lists individual tracks, define Recently Added semantics, test playlist lifecycle and add regression coverage for Music navigation.

### P0 — File operations and permission recovery

1. Rename and delete have separate DocumentsContract and MediaStore paths and handle RecoverableSecurityException, but provider-specific failure paths are not covered by tests.
2. Multi-file delete invokes the native delete bridge per selected URI. Partial success is possible; the UI needs explicit per-file results and a predictable refresh/reconciliation policy.
3. Several native scanning/document-provider paths catch exceptions without surfacing structured diagnostics. A failed scan can look like a legitimate empty or incomplete library.
4. Share, rename and delete need verification for MediaStore items, SAF documents, SD cards, USB-OTG and revoked grants.

**Required before v1.7 release:** explicit operation result reporting, partial-failure handling, refresh after successful operations, and tests across MediaStore and SAF URIs.

### P1 — Scanner, cache and folder catalogue

1. The source uses a WebView LocalStorage cache plus a native thumbnail cache. There is no Room database dependency or Room entity/DAO implementation in this branch. If durable indexed metadata and transactional cache updates remain a goal, they are outstanding.
2. Cache startup, large-library memory pressure, stale cache invalidation and concurrent refresh behavior have not been measured on-device.
3. SAF traversal has a bounded scan and preserves entries for incomplete scans, but slow, malformed and non-standard document providers remain a compatibility risk.
4. Folder identity/deduplication relies on stable path identity where available and exact URI otherwise; generic providers can expose duplicate physical content through different URIs.
5. All Folders/Folders/Files semantics and defaults need regression coverage, including upgrades from prior preference schema versions.

**Required before v1.7 release:** benchmark cold/warm launch and large libraries, verify all three content modes, test permission loss and partial scans, and document the cache source of truth.

### P1 — Playback controls, background behavior and storage

- Test direct timeline tap, thumb drag, rapid seeking and end-of-file behavior.
- Test gesture axis locking and ensure seek, brightness and volume do not overlap.
- Test rotation, screen-off playback, notification controls, Bluetooth/headset controls and PiP transitions.
- Test persisted SAF grants, revoked grants, SD card removal/reinsertion and USB-OTG disconnection.
- Test large folder traversal and slow provider responses without UI stalls or app termination.

### P1 — Vault security and recovery

1. AES-GCM encryption and Android Keystore use are present in source.
2. Decrypted playback files are stored under app cache and cleanup is attempted during activity destruction. Process termination, force-stop, crash and device reboot can bypass normal cleanup.
3. The encryption key is device/Keystore-bound. There is no user-facing recovery/export mechanism documented; key invalidation or loss can make stored vault data unrecoverable.
4. The existing roadmap acknowledges dedicated PIN/biometric access and production-grade recovery/key management are not complete.

**Required before promoting Vault as production-grade:** threat-model review, crash/force-stop cleanup tests, key invalidation/recovery policy and clear user warning about data loss. Do not represent the Vault as recoverable until implemented and tested.

### P2 — Subtitles and audio refinements

- MicroDVD conversion currently assumes 25 fps; selectable FPS is not implemented.
- Subtitle pinch shares touch-space with video zoom; independent subtitle sizing/gesture behavior needs validation.
- Audio timestamp offset and PCM gain are implemented but vary with codec, passthrough and device output path.
- Playback speed pitch preservation and Bluetooth profile compatibility require device tests.

## 3. Release metadata and documentation inconsistencies

1. Android Gradle config declares `versionCode = 22` and `versionName = "0.2.20"`, while the development work is described as v1.6 and the next milestone as v1.7. Establish a deliberate versioning scheme before release; do not silently change it during this audit.
2. PR #17's description still says the Folders catalogue is the default and references preference schema v3. The audited branch now defaults to **All Folders** and writes schema v4. Update the PR description before merge.
3. The feature roadmap's branch note says work is on `draft/android-player`, but the audited source is on `feature/v1.6-home-folder-catalogue`. Correct the stale branch note.
4. README says the Android source/APK workflow is maintained on `main`; current v1.6 work is still on a feature branch. Make the distinction explicit.
5. Android minimum SDK is 33 and configured ABI is arm64-v8a only. This is consistent with the current Android 13 / 64-bit target but excludes older Android versions and 32-bit-only devices. Treat this as a deliberate support policy.

## 4. Automated test and CI gap

Repository review found no Android unit-test or instrumentation-test source set and no test dependencies declared in the app Gradle file. The Android workflow currently performs:

- Inline player JavaScript extraction and `node --check`.
- Java/Gradle setup.
- Persistent preview signing-key validation.
- `gradle --no-daemon assembleDebug`.
- APK size reporting and release asset publication.

It does **not** run Gradle unit tests, Android instrumentation tests, emulator playback tests, lint, dependency verification or a codec sample suite.

**Stage B recommendation:** add tests in layers—pure JavaScript/navigation logic, Android unit tests for URI/metadata/identity helpers, then device/emulator smoke tests. Keep test-only dependencies out of the shipped APK.

## 7. APK size baseline and dependency policy

The most recently verified preview before this audit was Build #407 from commit `c6e847a`, with an APK reported at approximately **17.35 MB**. Record the exact artifact digest and byte size before dependency changes; 17.35 MB is a baseline reference, not a guarantee for future builds.

Every major dependency change must include before/after APK byte size and MB, delta in bytes and percentage, dependency change list, ABI/native-library contribution, affected-format playback regression results, and confirmation that the shipped APK remains below 45 MB.

No LibVLC or second heavyweight playback engine is approved. Keep Media3/ExoPlayer + NextLib.
